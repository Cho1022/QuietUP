# 거주 인증과 사용자 간 비식별 원칙

## 문서 목적

QuietUp의 향후 소음 알림은 발신자와 수신자가 실제로 해당 아파트 세대에 거주할 권한이 있는지 서버에서 확인할 수 있어야 합니다. 이 문서는 현재 구현된 아파트·동·세대·거주 관계, 1회용 코드 검증 흐름, 동시성 제어와 사용자 간 비식별 경계를 설명합니다.

현재 구현은 실제 행정기관 또는 관리사무소 시스템과 연동된 것이 아닙니다. MVP에서는 관리 주체가 사전에 발급한 1회용 코드의 해시를 DB에 적재한다고 가정하며, 코드 발급과 관리 시스템은 후속 범위입니다.

## 도메인 관계와 거주 정책

도메인은 다음 순서로 연결됩니다.

```text
아파트 단지(ApartmentComplex)
  → 동(ApartmentBuilding)
  → 세대(ApartmentUnit)
  → 거주 관계(Residence)
```

- 한 아파트 단지에는 여러 동이 있습니다.
- 한 동에는 여러 세대가 있습니다.
- 한 사용자는 한 개의 인증된 거주 세대만 가질 수 있습니다.
- 하나의 세대에는 가족 구성원 등 여러 사용자가 거주할 수 있습니다.
- 같은 세대를 인증하는 사용자도 각자 다른 1회용 코드를 사용해야 합니다.
- 이사, 거주 해제와 과거 거주 이력은 현재 범위에 포함하지 않습니다.

DB의 `residences.user_id`에는 unique 제약을 적용해 한 사용자의 다중 세대 인증을 차단합니다. `residences.unit_id`에는 unique 제약을 적용하지 않아 한 세대의 다중 거주자를 허용합니다.

## 1회용 코드 검증 흐름

`POST /api/v1/residences/verify` 요청은 다음 순서로 처리됩니다.

1. Access Token의 subject로 현재 사용자를 확인합니다.
2. 사용자가 이미 거주 인증을 완료했는지 확인합니다.
3. 요청한 아파트·동·세대 조합을 조회합니다.
4. 코드의 앞뒤 공백을 제거하고 영문을 대문자로 변환합니다.
5. `[A-Z0-9-]{8,32}` 형식을 검사하고 SHA-256 해시를 계산합니다.
6. 코드 해시 행을 `PESSIMISTIC_WRITE`로 잠가 조회합니다.
7. 코드가 요청 세대용인지, 만료되거나 사용되지 않았는지 확인합니다.
8. 거주 관계를 생성하고 코드 사용 시각과 사용자를 같은 트랜잭션에 기록합니다.

코드의 내부 하이픈은 제거하지 않습니다. DB에는 64자리 lowercase SHA-256 해시만 저장하며 코드 원문은 저장하거나 로그에 출력하지 않습니다.

## 동시 사용과 트랜잭션

거주 인증 전체는 서비스의 단일 트랜잭션에서 처리됩니다.

- 같은 코드를 여러 사용자가 동시에 제출하면 코드 해시 행의 비관적 잠금으로 한 요청만 성공합니다.
- 같은 사용자가 서로 다른 코드를 동시에 제출하면 `residences.user_id` unique 제약이 최종 방어선으로 동작합니다.
- 사용자 unique 충돌은 HTTP 409 `RESIDENCE_ALREADY_VERIFIED`로 변환합니다.
- 실패한 트랜잭션에서는 코드의 `used_at`, `used_by_user_id` 변경도 함께 롤백됩니다.

코드가 없거나, 만료됐거나, 이미 사용됐거나, 다른 세대용이거나, 요청 세대가 존재하지 않는 경우에는 모두 동일한 HTTP 400 `INVALID_RESIDENCE_VERIFICATION` 응답을 반환합니다. 외부 응답만으로 세대나 코드의 존재 여부를 구분하지 않도록 하기 위한 정책입니다.

## 사용자 간 비식별성

QuietUp이 현재 제공하는 익명성은 사용자 간 비식별성입니다.

> QuietUp은 사용자 간 실제 신원을 노출하지 않지만, 신고·차단·도배 방지와 권한 검증을 위해 서버 내부에는 사용자와 거주 세대의 매핑을 보관합니다.

서버는 인증과 권한 검증을 위해 사용자의 내부 ID, 이메일, 아파트 단지·동·호수와 거주 관계를 알고 있습니다. 따라서 서버 운영자로부터도 신원이 숨겨지는 완전한 익명 시스템은 아닙니다.

외부 API는 다른 사용자에 대해 다음 정보를 반환하지 않습니다.

- `users.id`, 이메일, 닉네임과 JWT subject
- `residenceId`, `apartmentUnitId`와 DB 외래키
- 실제 동·호수
- Firebase UID
- 인증 코드 해시, 사용 시각과 사용 사용자
- 같은 세대 또는 같은 동에 거주하는 다른 사용자 정보

아파트 검색 응답은 단지 ID·이름·도로명 주소만, 동 조회 응답은 동 ID·동 번호만 반환합니다. 본인 거주 상태 API는 현재 사용자 자신의 단지·주소·동·호수·인증 시각만 반환하며 내부 ID는 반환하지 않습니다.

## API와 권한 경계

현재 거주 도메인의 API는 모두 Access Token 인증이 필요합니다.

- `GET /api/v1/apartments?query={검색어}`: 이름 또는 주소로 최대 20개 단지 검색
- `GET /api/v1/apartments/{apartmentId}/buildings`: 해당 단지의 동 목록 조회
- `POST /api/v1/residences/verify`: 현재 사용자의 1회용 코드 거주 인증
- `GET /api/v1/residences/me`: 현재 사용자의 거주 인증 상태 조회

특정 사용자나 특정 세대의 거주자를 조회하는 외부 API는 제공하지 않습니다. 향후 소음 알림 기능은 같은 서버 애플리케이션 내부에서 현재 사용자의 인증된 거주 관계를 권한 검증에 사용할 수 있지만, 다른 사용자에게 실제 Residence 식별자나 동·호수를 반환해서는 안 됩니다.

## 현재 미구현 범위

- 실제 관리사무소 또는 행정기관 연동
- 인증 코드 발급·폐기·조회 관리자 기능
- 이사와 거주 해제 및 과거 거주 이력
- 소음 알림과 소음 방향 계산
- Android REST 연결

이 문서는 위 기능이 구현된 것으로 간주하지 않습니다.
